# Token 效率工程（上下文预算方法论）

> 适用场景：任何「提示词驱动多轮对话 / 多 Agent 协作 / 反复加载项目资料」的工作。产出的提示词只要涉及这些场景，就应把本文的模式内置进去。
> 核心事实先记住三条：**输入 token 每轮重收**（第 1 轮读进上下文的资料，第 N 轮还在被计费）；**工具结果永久留存会话历史**（一次全量测试输出会被后续每轮重发）；**多 Agent × 多轮次是乘法关系**（10 个 agent 各带 10 万 token 常驻跑 30 轮 = 3000 万 token）。
> 结论：省 token 的正确姿势是「**少读几遍、常驻集变小、产出结构化**」，不是「读浅一点」。读浅会丢约束，返工一轮吃掉的 token 比省的多。

## 一、为什么账单会爆（一个典型形状）

某多 Agent 项目单期消耗约 1.1 亿 token，而其全部静态资料（提示词、报告、反馈、参考代码）合计仅约 35 万 token——相当于**全量资料被重复读取约 300 遍**。病灶不是资料太多，而是：

- 每个执行 Agent 的每轮上下文都背着全套资料；
- 历史期次的报告/提示词全文被反复重读；
- Agent 自己写自由散文报告，下一期又被其他 Agent 全文重读；
- 没有台账，没人知道 token 花在哪。

## 二、五项可复用模式（按需写入你产出的提示词）

### 模式 1 · 三层 Boot 加载协议（前置加载，先于一切执行）

让 Agent 用最小代价获取项目绝对状态，替代「把所有文档读一遍」：

| 层 | 做法 | 开销 |
| :--- | :--- | :--- |
| 第一层·实时状态 | 用**命令**取当前状态（版本、git 状态、测试结果末行），不靠文档快照——文档可能滞后于磁盘实际 | ≈数百 token |
| 第二层·全读 | 只全读**小而关键**的文件（红线/纪律/清单类，各 ≤ 几 KB） | ≈4K token |
| 第三层·选节 | 大文档**只读相关节**（先看目录/标题，按节读），禁止通读 | 按需 |

**自检锚点（必备）**：加载完成后必须能一句话答出固定 N 问（当前版本？测试基线？最近进展与遗留？未提交改动？我的常驻规格是哪份？），答不出 = 没读完，答完即开工、不重读第二遍。

### 模式 2 · 常驻契约文件（规划与执行分离）

多 Agent / 多批次项目里，为**每批次**产出一份常驻契约文件（如 `docs/current-sprint.md`，**≤2000 字**），作为执行 Agent 的唯一规格来源。必含：本批任务裁剪版、触碰文件清单、红线摘要、验收判据、相关文件路径（供按需读取）、禁止扩大范围声明。宽阅读（历史资料、参考代码）只由规划 Agent 在规划期做一次，结论浓缩进契约文件——成本摊销。

### 模式 3 · 结构化产出 + 本地脚本渲染

Agent 只输出 JSON（数百 token），本地脚本把 JSON 填进既有模板生成人读文档（**模板一字不改**）。两条铁律：

- **Agent 不得自报验证结果**——脚本实跑测试/检查后回填真实字段（如 `tests.passed`），杜绝幻觉数字；
- **JSON 原件与渲染产物双落盘**——人读渲染产物，下一轮 Agent 只读 JSON。报告的消费侧才是反复发生的地方，这一条让节省变成复利。

### 模式 4 · 索引预热（index-then-fetch）

先读**索引**（几百 token：文件名 + 一句话摘要 + frontmatter 关键字段），判定需要什么，再按需读**单文件全文**。典型应用：

- 技能/能力清单：读 frontmatter（name/description/triggers），只精读命中的 1~2 个正文；
- 历史报告：读「期次 → 文件 → 一句话结论」索引，只精读最近一期；
- 目录树/文件地图：**只查不读**——找文件先 grep 树再 read_file，不背内容。

### 模式 5 · 上下文复利三杠杆

1. **会话历史压缩**：长会话只保留最近 N 轮完整 + 更早折叠为摘要，禁止带全量历史跑全程；
2. **大输出不进历史**：全量测试/构建由脚本代跑，会话内只回灌一行结论（如 `217 用例全绿`）；
3. **thinking 预算**：推理模型的思考 token 设硬上限（规划可放宽、执行收紧）。

## 三、禁读清单模式

在提示词里显式列出**不加载**的内容与替代方式：

| 常见禁读对象 | 替代方案 |
| :--- | :--- |
| 各历史版本提示词/方案书全文 | 当前版提示词内化口径；确需考古走单文件按需 |
| 全部历史报告/复盘 | 索引 + 只精读最近一期 |
| 全量反馈/需求/参考资料 | 索引 + 按需单文件 |
| 与本任务无关的技能正文 | 技能索引 + 按需精读命中项 |

配套纪律：给出**相关文件路径清单**让 Agent 按需读取（给路径不给全文）；「批量通读资料」写进 must_not。

## 四、测量先行（没有台账就没有优化）

1. **记账**：按 Agent / 按批次 / 按「固定加载 vs 按需读取」统计 token（对齐产品内已有的用量台账口径）；
2. **硬指标**：把 token 预算写成可验收判据（如「单 Agent 常驻规格 ≤3K token」「单批次总消耗 ≤X」），像测功能一样测消耗；
3. **闭环**：先测量 → 再砍 → 复测，每轮迭代记录节省比例；未达标须写明原因。

## 五、写进提示词的最小模板段

以下骨架可直接复制进产出的提示词（按目标项目填充）：

```
### 0.0 前置加载协议（先于一切执行）
> 目标：用最小 token 获取项目绝对状态。三层加载 + 自检，禁止通读大文档。

第一层·实时状态（命令取）：版本命令、git status/log、测试命令末行统计。
第二层·全读（小而关键）：<红线/纪律/清单类文件，各一行"读取目的">。
第三层·选节：<大文档> 只读 <具体节名>；<目录树/地图> 只查不读。

禁读清单：<历史版本全文>、<全部历史报告>、<全量资料>——已内化于本提示词
<context>；确需细节走 <ref_*> 单文件按需读取。

自检（N 问，答不出=没读完；答完即开工，不重读）：<固定问题列表>
```

## 六、常见反模式

- 把全部项目资料塞进每个 Agent 的每轮 system；
- 让 Agent 自报「测试通过」（无脚本实跑证据）；
- 报告写成自由散文，下一轮被其他 Agent 全文重读；
- 给结论不给路径（Agent 只好把源文件全读一遍）；
- 没有台账的「感觉省了」。

## 七、速查决策表

| 场景 | 动作 |
| :--- | :--- |
| 提示词要 Agent 自己读项目资料 | 加模式 1（三层 Boot）+ 自检锚点 |
| 多 Agent / 多批次项目 | 加模式 2（常驻契约）+ 模式 3（JSON 产出） |
| 历史资料/报告越积越多 | 加模式 4（索引预热）+ 禁读清单 |
| 长会话、大输出、推理模型 | 加模式 5 三杠杆 |
| 要证明省了 | 加第四节（台账 + 硬指标） |
