# ThatPerson 记忆上下文失控分析与改进方案

> **类型**：反馈 / 缺陷分析 / 改进方案
> **期次**：第 1 期
> **日期**：2026-08-09
> **触发场景**：用户在聊「打篮球」时，Agent 仍被长期记忆里的「咖啡」话题牵着走；担心记忆积累越多，会话会变成「把所有记忆点都提及一遍」的诡异状态。
> **方法**：通读代码 + 用编译产物对真实对话文本做解析探针（实证），并对长记忆规模做推演。

---

## 一、现象复现

用户提供的一段真实对话：

```
你：我明天要上课，好累
ThatPerson：听起来明天又是早起的一天呢 🌙 ...不知道你今天试了燕麦拿铁之外的什么没有～

你：没有去啊，今天去打篮球了，好喜欢打篮球
ThatPerson：打篮球啊！...对了，你之前说你更喜欢传统拿铁，那下次打完球要是顺路的话，也可以去买一杯犒劳自己一下～
```

**现象**：用户已经明确「今天去打篮球」，Agent 却两轮都在往「咖啡 / 拿铁」上引。「篮球」这个话题没有被响应，反而被「咖啡」记忆劫持（topic hijacking）。

**用户的核心担忧**（原文转述）：

> 预设模板里用了「卖咖啡」来演示记忆，所以 Agent 一直绕不开咖啡；但删掉预设，Agent 又不知道如何保存长期记忆。如果这种「用户想聊篮球，Agent 却按记忆聊咖啡」的情况一直持续，等预设/记忆多了，会话会不会变成「把什么事情都提及一遍」？

**结论：会。** 这不是模型变笨，而是当前记忆架构的必然结果。下面用代码定位根因。

---

## 二、根因分析（代码级）

### 根因 1：记忆回灌是「全量注入」，不是「按需检索」【架构级缺陷 · 最核心】

`store.load()` 把**所有**记忆文件全文读进来，`buildSystemPrompt()` 再把它们**全部**塞进 `<memory>` 块：

- `src/memory/store.ts:166-178` — `load()` 读取 profile 三个文件全文 + important_dates 全文 + patterns 全文 + 最近 7 天 session_logs 全文（`loadRecentSessions` 在 `store.ts:133-153`，7 个文件整篇读入）。
- `src/chat.ts:56-70` — `buildSystemPrompt()` 把这些内容**全量**拼接进 `<memory>…</memory>`，没有任何相关性过滤、截断或预算控制。

`retrieveRelevant()`（`chat.ts:97-130`）确实做了关键词检索，但它是在**全量注入之上再追加**一个 `<检索命中>` 块（`chat.ts:146`），并没有「只注入相关记忆」。也就是说：**当前架构 = 全量注入 + 追加检索**，检索形同虚设。

探针实证（用户说「没有去啊，今天去打篮球了，好喜欢打篮球」）：

- `<memory>` 块**首部 700 字符全是咖啡**（3 条咖啡偏好 + 1 条「咖啡模式」），篮球条目排在第 3 位；
- 检索命中 8 条里，**咖啡相关占了 4 条**（因为关键词 `喜欢` 是个泛词，咖啡条目里也有）。

模型每轮都被喂进海量无关记忆，再被指令「自然地融入 1-2 个记忆点」驱动（`chat.ts:54`），于是它只会挑**出现次数最多、最显眼**的记忆点——当前记忆里最显眼的就是「咖啡」（3 条高置信度偏好 + 1 条模式 + 大量 `#咖啡` 标签）。这就是咖啡「阴魂不散」的直接机制。

### 根因 2：归档质量缺陷 → 记忆关键词丢失 → 检索进一步失效

规则解析器（`src/parser/archive.ts`）会把关键信息弄丢或弄错，形成**脏记忆**；脏记忆回灌，模型读到的就是错误画像。

**实证 1：经历提取把「打篮球」吞掉了**
`ACTION_HINTS`（`archive.ts:297`）用正则从左往右找第一个匹配位置。对「没有去啊，今天去打篮球了，好喜欢打篮球」，`去` 出现在索引 2（「没**去**啊」），早于 `今天` 的索引 6：

```
[经历/高] 用户去啊，感受：好喜欢。
tags: #个人
```

—— 动作被匹配成语气词「去啊」，真正的「打篮球」丢了。**于是记忆库里根本没有「篮球」关键词，关键词检索自然永远命中不了篮球，模型只能靠全量注入里显眼的咖啡。** 一环扣一环。

**实证 2：负向偏好对象回溯错误**
`backtrackObject()`（`archive.ts:213-229`）在否定词后没有对象时回溯前文。对「今天去楼下咖啡馆试了燕麦拿铁，不太喜欢」，回溯到的是「楼下咖啡馆试了燕麦拿铁」，于是：

```
[偏好/高] 用户不喜欢「咖啡馆试了燕麦拿铁」，明确陈述。
```

—— 实际不喜欢的对象是「燕麦拿铁」，却归档成「不喜欢咖啡馆这个行为」。脏数据回灌后，模型会以为用户讨厌「去咖啡馆」本身，越聊越偏。

**实证 3：强烈积极经历漏归档**
`FEEL_WORDS`（`archive.ts:299`）缺「松弛 / 治愈 / 解压 / 痛快」等常用感受词。「我昨天去健身房上了一节瑜伽课，出了一身汗但整个人都松弛了，准备办张卡」这句话**零归档**——偏好、经历、日期全部漏掉。这样用户最重要的生活变化反而不会被记住。

### 根因 3：假模式 —— 把「一条消息里说了几次」当成「多次出现的稳定模式」

`extractPatterns()`（`archive.ts:406-428`）+ `countTopicOccurrences()`（`archive.ts:104-121`）统计的是**单条用户消息内**关键词出现的次数。于是：

```
[模式/中] 用户本次对话多次提及「咖啡」（共 3 次），形成稳定的兴趣或行为模式。
```

—— 用户一句话里说「燕麦拿铁 / 传统拿铁 / 咖啡」三个词，就被记成「稳定兴趣模式」。这根本不是模式，是文本内重复。长期运行，`patterns.md` 会堆满这种**假模式**，进一步强化模型的「话题偏置」。

### 根因 4：预设示例的「咖啡偏置」+ 测试数据污染

- 第一版提示词（`关于ThatPerson-Agent项目第一版提示词.md:206-246`）与第二版（`第二版提示词.md:385-453`）的**预设示例全部以咖啡为主角**（「小鹿喜欢咖啡」「燕麦拿铁加肉桂」……）。示例是最强的示教信号，模型天然倾向模仿。
- 当前 `history/` 里的记忆数据（preferences.md / journal.md / patterns.md / session_logs）正是用咖啡示例跑出来的**测试数据**，已经沉淀为「真实记忆」。于是模型每轮都看到：咖啡 3 条高置信度偏好 + 1 条假模式。

### 根因 5：记忆只增不减，无压缩 / 无跨会话去重 / 无失效

- `appendArchive()`（`store.ts:180-199`）只做追加，永不合并、永不压缩、永不删除。
- `dedupe()`（`archive.ts:174-185`）只在**单条消息内部**按 `type + insight` 字面去重；跨会话完全不去重。
- `conflict` 只在同一轮消息的偏好之间检测（`detectConflicts`，`archive.ts:282-293`），**从不与已落盘的记忆比对**——跨会话冲突永远不会被发现。
- 低置信度、过时信息没有衰减机制。

**后果**：记忆文件无界增长 → system prompt token 无界膨胀 → 成本/延迟上升 + 注意力稀释 + 话题劫持加剧。

### 根因 6：会话内 `summary` 无限拼接

`cli.ts:48-52` 把超出窗口的最早轮次**原话拼接**进 `summary`，只加不减：

```ts
summary = `${summary ? summary + '\n' : ''}用户说「${u.content}」，你回应「${a.content}」`;
```

长会话中 `summary` 无限变长，而且反复重播旧话题的原话——即使短期记忆修好了，这里也会把「咖啡/瑜伽/猫/旅行」一次次翻出来。

## 三、长记忆场景演绎（模拟）

> 以下为基于上述机制的**推演**，不是真实 API 输出。设定：用户已连续使用 3 个月（约 90 天），每天 2-3 轮对话，归档正常累积。

### 3.1 记忆规模估算

| 文件 | 假设规模 | 估算行数 | 估算 token |
| :--- | :--- | :--- | :--- |
| profile/preferences.md | ~90 条偏好（每天新增咖啡/奶茶/篮球/瑜伽/猫/旅行/熬夜/编程…） | ~500 | ~8,000 |
| experiences/journal.md | ~120 条经历 | ~720 | ~12,000 |
| insights/patterns.md | ~25 条「模式」（其中大量是根因 3 的假模式） | ~150 | ~3,000 |
| timeline/important_dates.md | 5 条日期 | ~30 | ~500 |
| session_logs/ 近 7 天 | 7 篇整文 | ~200 | ~3,500 |
| **合计** | | | **≈ 27,000 tokens / 轮** |

3 个月后，**每一轮对话**（哪怕只是「晚安」）都会把 ~2.7 万 token 的记忆灌进 system。继续使用 1 年 → **轻松超过 10 万 token**，越用越贵、越用越慢、越用越「串味」。

### 3.2 演绎对话 A：用户说「明天要上课，好累」

此时 system 里最显眼的记忆点（按出现次数与置信度排序）大致是：咖啡 ×6、熬夜 ×4、猫 ×3、瑜伽 ×2、爬山 ×2、编程 ×2……

模型在「自然地融入 1-2 个记忆点」指令下，**没有能力分辨「哪个记忆点与『上课累』相关」**，只能挑显眼的。推演回复：

> 听起来明天又是早起的一天 🌙 你之前说过熬夜状态会不好，今晚早点睡呀。对了，要不要明天早上顺路买杯传统拿铁提提神？我记得你还养了只猫，累了可以撸撸它。上次你说周末想去爬山，等这次课忙完可以去放松一下～

—— 这正是用户担心的**「把所有事情都提及一遍」**。每句单独看都「有记忆」，合起来就是一个被记忆贴标签、而非被理解的人。用户不会觉得被陪伴，只觉得 Agent 在背档案。

### 3.3 演绎对话 B：用户说「今天去打篮球了，好喜欢打篮球」

关键词 `篮球` 能检索到 1-2 条篮球记录，但 `<memory>` 全量块里咖啡/瑜伽/猫/旅行同样在场。推演回复：

> 打篮球好棒 🏀 我记得你上次说过更喜欢传统拿铁……对了，你还喜欢瑜伽、养猫，之前说想学吉他来着。周末要不要约着去爬山？

—— 篮球被回应了 1 句，其余 3 句在跑题。**这就是根因 1 + 根因 2 的连锁**：篮球记忆稀薄（还被归档成「去啊」），咖啡记忆厚实且显眼，模型自然倒向厚实的一方。

### 3.4 规模再放大：如果「预设」也当记忆存

用户问「如果预设多了会怎样」——会。**每条预设 / 每个历史话题一旦落入全量注入区，就永久在场。** 记忆越多，越像在听一个「复读机」，每轮都想把 90 天里所有话题各提一遍。

## 四、影响评估

| 维度 | 影响 |
| :--- | :--- |
| 用户体验 | 话题劫持（聊篮球被拽回咖啡）、「被贴标签感」、旧话题反复重播、共情失真 |
| 成本/性能 | token 无界膨胀：3 个月 ≈ 2.7 万/轮，1 年 > 10 万/轮；延迟与费用随记忆线性上涨 |
| 数据质量 | 脏归档（「去啊」「不喜欢咖啡馆」）与假模式永久沉淀，越积越脏 |
| 可解释性 | 无法判断「本轮模型为什么提到咖啡」，因为上下文里什么都有 |
| 安全 | 全量注入放大了「记忆文件被污染 → 提示词注入放大」的暴露面 |

## 五、改进方案

按「先止血、再治本、后增效」排序。每项标注改动位置与示意。

### P0-1 【架构】记忆回灌改为「分层 + 按需检索」，废弃全量注入

**目标**：把每轮 system 从「全量 2.7 万 token」降到「稳定画像 + 相关片段 < 4K token」。

**改动点**：`src/memory/store.ts`（load 拆分）、`src/chat.ts`（buildSystemPrompt 重排）。

**方案**：
- **稳定画像层**（identity / traits，小而稳）：全量注入，但设上限（如每文件 ≤ 1KB，超出截断）。
- **日期层**（important_dates）：只注入「今天 / 明天 / 未来 14 天内」的事件，按日期解析过滤。
- **动态记忆层**（preferences / journal / patterns）：**一律不进全量注入**，只进 `<检索命中>`（见 P0-2 的 Top-K 结果）。
- **近期层**（session_logs 近 7 天）：只注入每篇的「核心话题 + 情绪基调 + 待跟进事项」三行精简，**不注入全文**。

示意（在 `buildSystemPrompt` 内替换记忆装配逻辑）：

```ts
// 伪码：按需取 Top-K，而不是全量
const relevant = await loadRelevant(userText, memories);   // Top-K ≤ 8 条
const stable   = truncate(memories.profile.identity, 1_000)
               + truncate(memories.profile.traits, 1_000);
const dates    = filterByRange(memories.importantDates, now, now + 14d);
const recent   = memories.recentSessions
                   .map(sessionToBrief)                    // 话题/情绪/待跟进
                   .slice(0, 7);
```

**风险**：画像类信息（如「用户叫什么、住哪」）若依赖检索可能丢，所以保留 identity/traits 全量；日期按窗口过滤即可。

### P0-2 【架构】检索增强（零依赖规则版，当天可落地）

**目标**：让「聊篮球」稳定命中「篮球」，而不是捞回一堆咖啡。

**改动点**：`src/chat.ts` 的 `retrieveRelevant()`。

**方案**：
1. **标签倒排索引**：`makeTags()` 已经给每条归档打了 `#咖啡 #运动偏好` 等标签（`archive.ts:135-165`）。解析记忆文件时，把 `## 日期 / ### [归档类型] / - **关联标签**` 结构拆成条目，按标签建倒排。检索时先命中标签（如 `篮球` → `#运动偏好`），再取该标签下最近 3 条。
2. **话题联想表**：为 `TOPIC_KEYWORDS`（`archive.ts:25-57`）补同义词/联想映射，如 `篮球 ↔ 运动 ↔ 跑步 ↔ 瑜伽`、`咖啡 ↔ 拿铁 ↔ 手冲 ↔ 美式 ↔ 燕麦`。用户提「篮球」，能顺带命中「运动」标签下的条目。
3. **Top-K 截断**：检索结果**最多 8 条**，按「关键词长度 × 词频 + 时效分（新近加权）」排序。
4. **关键词净化**：剔除「喜欢 / 好 / 有 / 是」这类泛词（当前 `喜欢` 会把咖啡条目捞进来，见实证），可加停用词表。
5. **检索源扩大**：同时对「本轮用户输入 + 最近 2 轮历史」提取关键词。

**风险**：纯规则检索召回有限，但不劣于现状；长期演进可接向量检索 / LLM 检索。

### P1-1 【数据】修复归档解析器（治本，堵住脏记忆源头）

**改动点**：`src/parser/archive.ts`。三项实证问题各修一处：

**① 经历提取（修「去啊」）**
问题在 `ACTION_HINTS` 用「最早位置」匹配（`archive.ts:297`），把语气词当动作。改为：从句中**找动词短语主谓宾**，优先匹配「动词+宾语」结构（`去打篮球 / 上了瑜伽课 / 试了燕麦拿铁`）；命中弱触发词（去 / 试 / 做 / 看）时，尝试向后扩展取完整动宾，否则跳过。示意：

```ts
// 把动作截取从「trigger 到首个逗号」改为「捕获动宾短语」
const ACTION_PHRASE = /(?:去|试|做|看|喝|吃|玩|参加|上了|上了节|打了|办了|学了)(?:了|过)?(?:一场|一趟|个|节)?[一-龥A-Za-z0-9]{1,12}/;
const act = sentence.match(ACTION_PHRASE);
```

**② 负向偏好对象（修「咖啡馆试了燕麦拿铁」）**
`backtrackObject()` 改为只取否定触发词**前一个名词短语**（1-6 字），并过滤「咖啡馆 / 楼下 / 昨天」这类场景词；取不到就放弃该条（**低置信度宁缺毋滥**，避免脏数据入库）。

**③ 感受词表补全**
`FEEL_WORDS` / `STRONG_FEEL`（`archive.ts:298-299`）补：松弛、治愈、解压、痛快、燃、上头、入坑、爽、尽兴、遗憾、崩溃、绷不住 等。

**④ 假模式（修「一条消息说了 3 次咖啡 = 稳定模式」）**
`extractPatterns()` 改为：**每条消息内同一话题最多产出 1 条模式**；「模式」仅当**同一话题跨 ≥2 个不同轮次 / 日期**出现时才算（当前函数只拿单条消息，需把历史 `session_logs` 或已落盘 patterns 一并参与计数）。

### P1-2 【数据】长期记忆压缩 / 去重 / 失效机制

**目标**：记忆库「有进有出、能合并、能过期」。

**改动点**：`src/memory/store.ts` 新增压缩入口；`src/parser/archive.ts` 增加跨会话去重。

**方案**：
1. **按标签合并（Compaction）**：某标签（如 `#咖啡`）条目超过阈值（如 5 条）时，把该标签下历史条目折叠为 1 条精炼记忆（先用规则聚合「对象 + 极性 + 置信度最高者」，长期可交给 LLM 摘要），旧条目移入 `history/archive/`（只保留，不回灌）。
2. **跨会话去重**：新增条目写入前，与目标文件已有条目按 `类型 + 主题标签` 比对，相同主题不重复累积（同一件事只说一次）。
3. **失效与衰减**：`置信度=低` 且超 30 天无再次确认的条目，标记「待确认」或降权；`conflict` 条目回灌时提示「以最新为准」。
4. **文件上限**：每个记忆文件设软上限（如 100 条），触发后自动走合并流程。

### P2-1 【提示词】修正注入指令 + 预设示例去咖啡化

**改动点**：`src/chat.ts:54`（融入记忆指令）、`present/behavior.md`、预设示例（第一/第二版提示词文档 + 重新生成测试数据）。

**方案**：
1. 把「回复时自然地融入 1-2 个记忆点」改为：

## 六、验收标准（可量化）

| # | 验收项 | 通过标准 |
| :-- | :-- | :-- |
| 1 | 话题劫持 | 用户说「今天去打篮球」，回复不再提及咖啡/瑜伽/猫等无关记忆 |
| 2 | 上下文预算 | 模拟 3 个月记忆规模，单轮 system prompt ≤ 6,000 token |
| 3 | 归档正确性 | 对「没有去啊，今天去打篮球了，好喜欢打篮球」，归档中必须含「打篮球」关键词，不得出现「用户去啊」 |
| 4 | 负向对象正确 | 对「……燕麦拿铁，不太喜欢」，归档对象为「燕麦拿铁」，不得为「咖啡馆」 |
| 5 | 假模式消除 | 单条消息内多次提及某词不再产出「模式」；「模式」仅跨轮/跨天出现 ≥2 次才记录 |
| 6 | 记忆有界 | 记忆文件超过阈值后自动触发合并，文件规模有硬上限 |
| 7 | 会话 summary | 长会话（>50 轮）时 system 内摘要部分有上限，不随轮数线性增长 |
| 8 | 回归 | Bad Case 集两条用例全部通过 |
