# 总结

### 1. P0：记忆归档算法存在严重逻辑漏洞（示例三）

- **问题**：Agent 把“你记得我喜欢干什么嘛”中的“干什么嘛”当成了一项“喜欢”活动，把“不喜欢下雨天”同时归档成“喜欢”和“不喜欢”，出现冲突。
    
- **根因**：Agent 把“喜欢”和“不喜欢”当成了简单的关键词标签，没有结合句法结构判断语义方向。
    
- **后果**：随着对话增多，记忆库会自我矛盾，系统对用户的“画像”会逐渐混乱而不是越来越准。
    

### 2. P1：元认知仅是“功能描述”，未形成“自我意识”（示例一）

- **问题**：示例一中，CLI 提示“检查工作目录”后 Agent 没有执行具体动作，只是泛泛回应了“让我看看工作目录里有什么”，实际上没有检索目录。
    
- **根因**：第三版提示词描述了“你应该有元认知”，但 Agent 仅在生成回复的层面提及这个概念，没有在行为层面执行该概念对应的动作。
    
- **后果**：元认知仍是“工程师写给 Agent 看的说明书”，尚未转化为 Agent 的**行为约束**或**工作流**。
    

### 3. P1：Agent 对自己的“肢觉”无知（示例四）

- **问题**：用户明确要求“调用 vault-api-bridge skill”，Agent 回复“我没有这样的能力”，虽然提示词中定义过“检查 skill”，但 Agent 没有执行任何检查。
    
- **根因**：Prompt 定义了“能力边界”，但没有定义“能力边界自查机制”。Agent 不知道自己有什么技能，也不知道如何主动“检查技能”。
    
- **后果**：有 skill 但不会用，skill 系统形同虚设。
    

### 4. P2：CLI 与 Agent 的“执行层”脱钩（示例一）

- **问题**：用户输入“检查工作目录”后，CLI 退出，未将结果返回给 Agent 继续处理。
    
- **根因**：CLI 仅为“消息传递通道”，不具备“指令分发”能力。
    
- **后果**：Agent 的某些计划无法落地，系统显得“会说话但不会动”。

##  下阶段行动指南

### 1. 修复记忆归档逻辑（P0）

**直接在 `archive.ts` 中做以下改动（或提示词中约束）：**

- 对“喜欢”“讨厌”等情感动词做**极性判断**：
    
    - 提取谓语动词后的名词短语，判断情感方向（正面/负面）。
        
    - 若方向为正 → 归档为 `偏好`；方向为负 → 归档为 `厌恶`。
        
    - 无法判断极性 → 降为 `低置信度` 或标记为 `待确认`。
        
- 减少对单个词的依赖，转而采用**句法分析**或**情感极性词典**（可直接嵌入提示词）。
    

### 2. 构建“元认知行为”而非“元认知描述”（P1）

**在下一版提示词中，将“元认知”从“身份描述”变为“行为开关”：**

- 在 system 中加入：
    
    text
    
    如果你不确定某件事能否执行，必须先执行一次“能力自查”：检查 present/ 目录下是否有对应指令，再回应。
    
- 为 Agent 增加“能力自查”操作：
    
    - 当用户问题涉及“你能/你可以吗”，先触发一次 `read present/` 指令（在 CLI 中实现）。
        

### 3. 让 Agent 拥有“肢觉”——知道自己有什么 skill（P1）

**将 skill 系统与 Agent 的“自我描述”绑定：**

- 在 `present/` 中增加一个文件 `skills-manifest.md`，用自然语言描述当前已安装的技能列表。
    
- 在 system prompt 中要求：
    
    text
    
    当用户提到“技能/调用/执行”时，先读取 skills-manifest.md，再回复可用的技能。
    

### 4. 完善 CLI 的“指令-执行-返回”循环（P2）

**将 CLI 从“消息通道”升级为“指令执行器”：**

- 为 CLI 预留“可执行指令”判定：
    
    - 用户输入若以 `/` 开头，如 `/check directory`，CLI 先执行该动作，将结果拼接后再送入 LLM。
        
- 这样 Agent 的“检查工作目录”“读取日记”等需求，就能真正被实现。
