## 二、P1 技能无法执行 —— 完全成立（架构性缺失）

### 2.1 用户判断

> 从代码中就可以看出只有 skill（发现 -> 匹配 -> 加载）……我们现在需要**重写工具调用层**，不去修"它为什么意识不到手"，而是去重新设计手——把 Tool 作为第一性概念。

### 2.2 证据链（代码级）

**① skill.ts 只实现"发现/匹配/加载"，无执行：**

- listSkills()（扫描 SKILL.md 目录）→ matchSkill()（slash/auto 匹配）→ loadSkill()（读 SKILL.md 全文）。三件事全是**读文本**，没有任何"执行"概念。
- SkillInfo 结构（name/description/triggerKeywords/dir/skillPath/content）里没有可执行入口字段（无 command、无 executor、无 tools 声明）。

**② cli.ts 的"工具通道"只有 1 个白名单指令：**

- TOOL_COMMANDS = new Set(['check'])（src/cli.ts）——唯一可执行的是 check directory（列目录）。
- detectToolIntent() 只识别「检查/查看/看看 + 目录」与「列出目录」两类意图。

**③ chat.ts 调用 DeepSeek 未传 tools 参数（无 Function Calling）：**

```
fetch(`${BASE_URL}/chat/completions`) 的 body 只有 { model, messages, stream: false }
没有 tools 与 tool_choice，模型无从返回结构化工具调用，只能"口头说想做什么"。
```

**④ vault-api-bridge 的"手"存在但接不上：**

- skills/vault-api-bridge/scripts/自动化脚本/ 下**确有** vault_api.py / vault_env.py / vault_reader.py 等可执行脚本。
- 但 SKILL.md 正文要求"运行 python vault_env.py""调用 api.execute(...)"——ThatPerson 代码里**没有任何 shell/python 子进程执行器**，技能正文只是一份读给模型听的说明书。

### 2.3 实测（驱动真实 dist 产物）

| 用户输入 | detectToolIntent 结果 |
| :-- | :-- |
| 从知识库中读取2026年7月31日的日记 | null（无任何工具意图） |
| 读一下 G:/XXFS/groWiki/6-日记/2026年7月31日.md | null（无任何工具意图） |
| 检查工作目录 | {"command":"check","args":"directory"}（唯一命中的意图） |
| 帮我把笔记归类 | null（warehouses-management 技能无法执行） |

### 2.4 结论

**问题成立，且性质确认为架构性缺失而非提示词 bug。** 对话中 ThatPerson"意识到自己有手但手抬不起来"（如实反馈"没有文件系统访问权限"）是**真实陈述**——因为代码里确实不存在任何文件读取工具。用户的判断（修架构而非修 bug）正确。

## 三、P2/P3 记忆归档质量问题 —— 成立（实测复现）

### 3.1 用户反馈

- 示例二：发送日记内容后，ThatPerson 没有在意日记内容本身，而是回应"发日记"这个动作。
- 归档数据：用户喜欢「就是一个人坐在窗户边上吹着风做」与 用户喜欢「事情」 两条来自同一句话；"用户做我的项目啦这是我今天的日记，感受：开心。" 这类近乎原文复述的"提炼"。
- 示例三：用户可能不喜欢「看书」，表述不确定，待确认。 与 用户看书，感受：不喜欢。 同时出现（同一不确定陈述被双重归档）。

### 3.2 实测（驱动真实 extractArchives）

| 输入原话 | 实测产出 | 问题 |
| :-- | :-- | :-- |
| 最喜欢的就是一个人坐在窗户边上吹着风做着自己喜欢的事情 | ①偏好/高：用户喜欢「就是一个人坐在窗户边上吹着风做」 ②偏好/高：用户喜欢「事情」 | 同一句产出两条；第二条为无意义残片（cleanObject 未过滤"事情"类占位词；extractPrefs 在同一句多个「喜欢」命中点重复提取） |
| 当然是继续做我的项目啦这是我今天的日记 | 0 条归档 | 日记类长文本/情绪内容完全漏报（extractExperiences 依赖"感受词+动宾短语"，无感受词即不产条目） |
| 后时候也会看看书，说实话我不确定我到底喜不喜欢看书 | ①偏好/中：用户可能不喜欢「看书」，表述不确定 ②经历/高：用户看书，感受：不喜欢 | 同一不确定陈述被双重归档；且"经历/感受：不喜欢"是**过度推断**（用户是"不确定"，不是"不喜欢"） |

### 3.3 根因定位

- extractPrefs（src/parser/archive.ts）：PREF_RULES 正则对同一句的多个「喜欢」锚点各自命中；cleanObject 只剥首尾语气词，未过滤无意义占位词（事情/东西/感觉/时候…）。
- extractExperiences：FEEL_WORDS 含「喜欢」类词，否定/不确定语境（"不确定我到底喜不喜欢"）命中后仍断言负面感受；dedupe 按 type+insight 去重，两条 insight 不同故不去重。
- extractArchives 的输入只有 userText 单轮，长文本（日记）缺少"内容感知"通道；detectMood/主题提取对粘贴型内容同样浅。

### 3.4 结论

**成立。** 第 3 期已修过一轮（动宾短语、否定前置等），但边界 case（同句多锚点、不确定陈述、长文本）仍复现；同时 P2 的"没在意内容"还涉及 LLM 上下文与回复指令层，需双层修复（详见解决方案文档 §B）。

## 四、其余问题逐项核对

### P4 首次部署不生成 ~/.thatperson/ —— 成立（设计缺口）

已有《ThatPerson全局部署首次引导问题分析与改进方案-20260812.md》详细核实，要点：

- ensureConfigDir() 确实会创建目录，但只在 main() 走到对话/子命令分支时调用；--version/--help（文档建议的"验证安装"第一步）提前 process.exit，**不创建目录**。
- **附带确认**：apiKeyGuidance() 是**死代码**——全仓 grep 无任何调用点；且提示语"用 config 指令配置"对应的 CONFIG_KEY_WHITELIST 里**没有 apiKey 键**，用户按提示也配不上。
- Key 读取只认环境变量；全局部署下 loadEnv() 读的是**包安装目录**的 .env 而非用户工作目录（现有 Open 文档 §2.2 已核实）。

### P5 配置向导缺失 —— 成立

- runGlobalCommand() 的 case 分支：status/update/help/memory/session/config/skills，**无 setup/wizard**。
- ThatPersonConfig 只有 model/disabledSkills 两字段，无 apiKey。

### P6 present/ 为空不提醒 —— 成立

- 无"空目录→提醒用户可填写"的逻辑；启动横幅（runDialog）也不提示 present 状态。

## 五、附带发现（核查中额外确认）

1. **apiKeyGuidance() 死代码**（P4 附带）：函数完整实现但无调用点，属"写了没用"的引导逻辑，与"配置向导缺失"同源。
2. **chat.ts 的人格句硬编码**：buildSystemPrompt 中「个人 AI 伴侣」等 3 句人格指令是写死的，未走 present 层——用户想自定义定位只能靠 present 覆盖同义表述，存在"双来源打架"风险。
3. **ensureConfigDir() 子目录清单不含 history/**（Open 文档已指出）：history/ 由 store.ensureStructure() 另行创建，两处职责分离但注释宣称目录含 history，文档与实现存在出入。
4. **skill.ts 与 cli.ts 的 Skill 扫描目录不一致**：skill.ts 默认扫描包内 skills/，cli.ts 的 defaultProjectSkillsDirs() 额外加了 .claude/skills；两套目录来源并存，未来工具层注册需统一口径。
