# ThatPerson 提示词「预设模板」去留与改进建议

> **类型**：反馈 / 提示词改进建议
> **期次**：第 1 期
> **日期**：2026-08-09
> **依据**：`项目资源文件/关于ThatPerson-Agent项目第一版提示词.md`（v3.0）与 `第二版提示词.md`（v2.0）全文对照 + 源码阅读（`present/`、`src/`、`history/`）
> **待答问题**：往后的提示词中，还需要提供预设模板吗？

---

## 一、结论先行

**需要保留预设模板，但要重构——分成三层，各司其职。** 直接删除是下策，因为预设是 Agent 的「出厂设置」，删了它 Agent 确实不知道怎么定义自己；但保留现在的样子更糟，因为它正在污染对话（咖啡劫持）并将持续污染下去。

同时有一个**关键认知要纠正**，它能直接化解你「删除预设 Agent 就不知道如何保存长期记忆」的担忧：

> **在 ThatPerson 里，保存长期记忆（归档）不是 LLM 的职责，是代码的职责。**
>
> `src/index.ts:33-37` 与 `src/cli.ts:54-58` 在每次对话后自动调用 `extractArchives()` + `store.appendArchive()` + `appendSessionLog()`，**全程不经过模型**。LLM 只负责聊天，从不负责写记忆。所以预设里即使删掉「记忆结构 / 归档格式」那一整块，ThatPerson **依然会自动保存长期记忆**——这些格式是给开发团队看的规范，不是给运行中的 LLM 看的指令。

> 一句话：**预设模板回答的是「Agent 是谁、怎么聊」，记忆保存由代码保证，不依赖预设。** 因此可以放心地对预设做减法。

---

## 二、为什么「还需要预设」：三层各自不可替代

| 层 | 回答的问题 | 现状载体 | 必要性 |
| :-- | :-- | :-- | :-- |
| **① 指令层（Agent 元认知）** | 我是谁 / 我的风格 / 我的准则 / 我的输出习惯 | `present/*.md`（每次对话加载进 System 最前） | **必须保留**。这是 Agent 的出厂设置，删了退回裸模型 |
| **② 示例层（格式演示）** | 回复长什么样 / 归档条目怎么写 | 两份提示词里的「示例 1/2/3」 | **保留但必须改造**（现为咖啡单主题，是污染源） |
| **③ 数据层（用户画像）** | 用户喜欢咖啡/篮球、养猫、职业…… | `history/*`（真实对话归档产生） | **与预设完全隔离**，不属于预设；当前被示例污染 |

现状的根本问题：**这三层被混在预设里一股脑复制**，尤其是「② 示例里的用户画像」被当成了「③ 真实记忆」——你跑测试跑出来的咖啡数据（`history/profile/preferences.md`、`experiences/journal.md`、`insights/patterns.md`）正是这么来的。

---

## 三、当前预设的三大问题（对照两份提示词原文）

### 问题 1：示例层被「咖啡」单主题垄断 → 冷启动偏置

第一版 v3.0 的「五、示例」三例（`第一版提示词.md:202-275`）与第二版 v2.0 的 `preset_examples`（`第二版提示词.md:382-453`）**全部以咖啡 / 健身为主题**：

- 示例 1：用户「小鹿，喜欢咖啡，上周刚入职」（v1:206-213）
- 示例 2：「燕麦拿铁加肉桂 / 更喜欢传统拿铁 / 咖啡馆环境」（v1:219-245）
- 示例 3：瑜伽（v1:254-274）

示例是提示词里**最强的示教信号**。全部咖啡 = 模型天然认为「这就是该聊的话题」。实测 `history/` 里的记忆正是这三例跑出来的：咖啡 3 条高置信度偏好 + 1 条「咖啡模式」。**示例从「教格式」变成了「注入画像」。**

### 问题 2：职责混淆——「Agent 元认知」和「用户画像」被塞进同一块

预设里既有「我是 ThatPerson，温暖细腻」（该有），也有「用户叫小鹿，喜欢咖啡，上周入职」（**不该有**）。用户事实属于 `history/`，属于真实对话的产物。预设里硬编码用户事实，等于在模型脑子里「预装」了一个虚构用户，之后所有真实归档都挤在这个虚构画像旁边。

### 问题 3：预设被复制了两份，双重维护必然漂移

第二版 changelog 明确写着「从第一版 v3.0 **同步**预设内容」（`第二版提示词.md:487`）。两份文档各自维护同一份预设，已经出现差异风险；第三期再改，漂移只会更大。**预设必须单一事实源。**

## 四、改进方案：预设「三层分离」重构

### 4.1 指令层：精简到只有「Agent 自身元认知」

`present/*.md` 保留身份 / 人格 / 行为准则 / 输出风格即可，**删除其中对用户画像的描述**。并加入上期反馈 P2-1 的**相关性约束**：

- 现在（`src/chat.ts:54`）：`回复时自然地融入 1-2 个记忆点` —— 无相关性约束，是全话题扫射的直接诱因。
- 改为：`只融入与当前话题或情绪直接相关的记忆点，最多 1 个；与当前话题无关的旧记忆忽略，不要提及。`

同时给 `present/behavior.md` 的「记忆优先」补一句前提：*关联记忆的前提是与当前话题相关，禁止为融入而融入。*

### 4.2 示例层：多主题中性 + 显式声明「仅演示格式」

- **示例主题去咖啡化**，改用多种中性主题轮换（如 篮球 / 加班 / 养猫 / 阅读 / 旅行），避免任何单一主题成为偏置。
- **示例前加显式声明**：`以下示例仅为演示回复与归档格式，禁止模仿其话题与措辞。`
- **示例里的用户用占位符**（如「用户」/「小鹿」），且不得与真实记忆混写。
- **示例中的「归档内容写入 history/…」段落**，在演示时不得真正写入 `history/`；演示数据一律使用独立根目录（`createMemoryStore(demoRoot)`），跑完即弃。

### 4.3 数据层：与预设彻底隔离 + 清洗历史污染

- `history/` 只由真实对话归档产生，**预设和示例永不直接写入**。
- **清空 / 合并现有演示数据**：当前 preferences.md / journal.md / patterns.md 里的咖啡条目是测试残留，建议清空后按上期方案（P1-2 压缩）重建为中性记忆，或直接删除让 Agent 从零积累。

## 七、往后的开发提示词应该怎么写（第三期起）

**推荐结构——「增量 + 引用 + 卫生要求」，不再背整份预设：**

```markdown
## 一、本期任务（tasks）
  （只写增量改动，不重复前两期全文）

## 二、变更说明（changelog）
  （引用前几期，标注「预设规范已迁往单一事实源」）

## 三、预设规范引用（不再内联）
  - 产品元认知（Agent 是谁/怎么聊）：present/*.md
  - 归档格式与记忆目录：src/parser/archive.ts、src/memory/store.ts、src/memory/types.ts
  - 生成规范：代码即规范，改动必须改代码而非改提示词副本

## 四、示例（如需）
  - 仅格式示例，多主题中性轮换，显式标注「仅演示格式，禁止模仿话题」

## 五、数据卫生（新增硬性要求）
  - 演示/测试数据一律使用 createMemoryStore(demoRoot) 独立目录
  - 每次迭代提交前检查 history/ 无测试残留
  - 真实记忆只由真实对话归档产生
```

**核心转变**：预设从「每期复制一份的正文」→「指向代码的单一事实源」。开发团队不再对着两份漂移的提示词副本实现，而是对着 `src/` 与 `present/` 的实际情况改。

---

## 八、一句话结论

> **还需要预设模板，但只需要「指令层 + 干净的多主题示例层」，并让它们指向代码这个单一事实源；用户画像与归档全部交给代码和真实对话，与预设彻底隔离。** 这样既保住 Agent 的「出厂设置」，又根除咖啡劫持和「所有话题提及一遍」的隐患。
