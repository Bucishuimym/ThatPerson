# ThatPerson 全局部署首次引导问题分析与改进方案（npm 部署 · Ubuntu）

> **类型**：反馈 / 部署缺陷分析 / 改进方案
> **期次**：第 4 期（发布后用户侧验证）
> **日期**：2026-08-12
> **触发场景**：在一台 Ubuntu 电脑上用 npm 全局部署 thatperson（只部署 Agent，不复制本项目）。用户报告三点：
>   1. 用户级目录下不会自动生成 `~/.thatperson/`；
>   2. 安装正常、`--version` 显示版本号，但**在线运行提示缺少 `AAGENTDS_API_KEY`**，需要自行在项目目录下新建 `.env`；
>   3. 面向「只部署、不复制项目」的人群，要求 Key 与配置模型同文件、首次部署有配置向导、用户级目录自动生成。
> **方法**：通读源码 + 核验 `dist/` 编译产物（npm 包实际行为）+ 对照 `README.md` / `使用说明.md` 文档描述。

## 一、问题核实结论（先给结论）

| # | 用户报告 | 核实结论 |
| :-- | :-- | :-- |
| 1 | `~/.thatperson/` 不会自动生成 | **部分成立（设计缺口）**。代码会在「完整进入对话 / 子命令」时创建该目录；但首次引导路径（`--version` / `--help`，恰是文档建议用户第一个执行的动作）不创建；且无「首次运行标记 / 向导」保证用户感知初始化成功。详见 §二.1。 |
| 2 | 缺 `AAGENTDS_API_KEY`，需在项目目录建 `.env` | **完全成立，且比报告更严重**。Key 只从环境变量读取，config.json 与 Key 是两套存储；`loadEnv()` 读的是**包安装目录**的 `.env`（`__dirname` 相对路径），不是用户的工作目录——即按文档「在工作目录建 .env」在全局安装下**也读不到**。详见 §二.2。 |
| 3 | 三点改进诉求 | **全部合理**。参考解决方案见 §四。 |

## 二、根因分析（代码级）

### 2.1 问题 1：`~/.thatperson/` 的创建时机不可靠

**证据链：**

- `ensureConfigDir()`（`src/config.ts:42-52`）确实会创建 `~/.thatperson/` 及其 `present/ skills/ logs/` 子目录并写默认 `config.json`。它只在 `src/cli.ts:750` 被调用。
- `src/cli.ts:730-750` 的 `main()` 执行顺序是：
  1. `loadEnv()`（731）
  2. `--version` → `process.exit(0)`（735-738）
  3. `--help` → `process.exit(0)`（740-743）
  4. `--mock` 相关 / 未知参数 → 提前退出（744-748）
  5. `ensureConfigDir()`（750） ← **只有走到这里才会创建目录**
- 文档《使用说明.md》§2.2「验证安装」让用户先跑 `thatperson --version`、`thatperson --help`——**这两个命令都不会创建 `~/.thatperson/`**。用户「安装正常显示版本号」后去用户级目录查看，自然看不到 `.thatperson/`。

**附带发现（次要缺口）：**

- `ensureConfigDir()` 的子目录清单只有 `['', 'present', 'skills', 'logs']`（`src/config.ts:44`），**不含 `history/`**；但文件头注释（`src/config.ts:4`）宣称 `~/.thatperson/` 包含 `history/`。实际 `history/` 依赖 `store.ensureStructure()`（`src/memory/store.ts:327-331`）另行创建，两处职责分离且未在注释/文档中说明。
- 没有任何「首次运行标记」（如 config.json 内 `configured: false`）或初始化向导，用户无法感知「初始化是否成功」。

**结论**：目录「在线运行时会创建」为真，但「首次引导链路不保证、用户感知不到」也为真。报告的现象成立，属于设计缺口而非「代码完全没实现」。

### 2.2 问题 2：API Key 与配置分离，且配置通道绑定「项目/包目录」

**证据链：**

- **Key 的唯一来源是环境变量**：`hasApiKey()`（`src/config.ts:209-211`）只读 `process.env.AAGENTDS_API_KEY`；`chat()`（`src/chat.ts:479-481`）同样只读环境变量，缺失即抛错「未找到 AAGENTDS_API_KEY，请检查项目根目录的 .env 文件」。
- **config.json 与 Key 是两套存储**：`ThatPersonConfig`（`src/config.ts:28-31`）只有 `model` / `disabledSkills` 两个字段；`CONFIG_KEY_WHITELIST`（`src/config.ts:25`）也只有这两个可写键。
- **`loadEnv()` 读的是「包安装目录」的 `.env`，不是 cwd**（`src/chat.ts:48-54`）：
  ```ts
  process.loadEnvFile(path.resolve(__dirname, '..', '..', '.env'));
  ```
  - 项目模式（`npm start` / `npm run dev`，`package.json:16-17` 用 `node --env-file=.env`）：`__dirname` 上溯两级 = 项目根 → 读到项目根 `.env`，开发者可用。
  - **全局部署模式**（`npm i -g` 后任意目录跑 `thatperson`，bin 指向 `dist/src/cli.js`，无 `--env-file`）：`__dirname` = `/usr/lib/node_modules/@nineteenfolk/thatperson/dist/src`，上溯两级 = **npm 全局包安装目录**。用户按文档在「自己的工作目录」建 `.env`，`loadEnv()` **根本读不到**。
- **引导文案与实现矛盾**：`apiKeyGuidance()`（`src/config.ts:218-225`）提示「在项目根目录 .env 中添加 AAGENTDS_API_KEY」；`chat.ts:481` 错误信息也写「检查项目根目录的 .env」；`README.md:14`、`使用说明.md:42-50` 均引导用户在「工作目录」建 `.env`。这些对全局部署人群都不成立。

**结论**：报告完全成立，且比报告更严重——不只是「需要手动配置」，而是「按文档配置了（在工作目录建 .env）也可能读不到」。配置通道把「Key」绑死在项目/包目录，而目标人群恰恰是「只部署 Agent、不复制项目」的人。

### 2.3 附带发现：`--mock` 以外的「在线」门槛

- `--mock` 可无 Key 运行（`chat.ts:480,483-485`），但 `--mock` 是离线演示，用户无法借此完成真实配置闭环。
- 用户一旦在线运行被 Key 错误打断，就没有任何「下一步可执行的配置指令」被清晰提示——`apiKeyGuidance()` 说「或稍后用 config 指令配置」，但 `config set` 白名单里根本没有 Key 键（`src/config.ts:25`），**用户按提示去配也配不上**。

## 四、参考解决方案（对应三点改进）

> 均为基础设计建议，具体实现待确认后推进。改动不覆盖既有文件、不静默改写，延续现有「已存在不覆盖」约定。

### 方案 1：API Key 并入 config.json（一文件管配置，Key 随用户走）

- `ThatPersonConfig` 增加可选字段 `apiKey?: string`；`CONFIG_KEY_WHITELIST` 增加 `apiKey`，使 `thatperson config set apiKey <key>` 可用。
- 新增集中解析函数（如 `resolveApiKey(): string | undefined`），优先级：**系统环境变量 `AAGENTDS_API_KEY` > config.json.apiKey > 既有包目录 `.env`（保留兼容）**。`hasApiKey()` / `chat()` 统一改走 `resolveApiKey()`，消除两处重复读取（`chat.ts:479` 现在直接读环境变量）。
- **安全配套**：
  - config.json 写盘时对 POSIX 设 `0600` 权限（`fs.writeFileSync` 后 `chmodSync`，或 `{ mode: 0o600 }`），避免明文 Key 被同机其他用户读取；
  - `thatperson config get apiKey` / `thatperson status` 一律**掩码回显**（如 `sk-***abcd`），延续「CLI 不打印 Key」红线；
  - `chat.ts` 错误信息改为「请运行 `thatperson setup` 或 `thatperson config set apiKey <key>`」。
- 该方案天然满足「Key 与配置模型同文件」，且 config.json 位于用户级 `~/.thatperson/`，Key 随用户走、不绑定项目。

### 方案 2：首次启动配置向导（成功后不再自动运行，可用 CLI 手动调动）

- 新增独立模块（如 `src/setup.ts`）提供 `runSetupWizard()`，职责：
  1. 显示 `thatPersonHome()` 与 config.json 路径；
  2. 交互式输入 API Key（`inquirer` 已依赖，用 password 类型掩码），**不打印、不落日志**；
  3. 可选步骤：确认/选择默认模型；
  4. 写回 config.json（保留既有字段，只新增 apiKey + `configured: true`）；
  5. 校验写入成功，提示重新运行 `thatperson`。
- 触发时机：`main()` 在 `ensureConfigDir()` 之后、进入对话之前，判断 `!isMock && !resolveApiKey() && !config.configured` 时自动进入向导。
- **不重复自动运行**：config.json 存在 `apiKey` 或 `configured: true` 即跳过；`--version` / `--help` / `--mock` / 管道非交互输入一律不弹向导（保持 CLI 可脚本化）。
- **手动重跑**：CLI 新增 `thatperson setup` 子命令（进 `runGlobalCommand`，`src/cli.ts:637-720`），可随时重配；非交互环境提示用 `thatperson config set apiKey <key>`。
- `apiKeyGuidance()` 改为指向向导：`未检测到 API Key，请运行 thatperson setup 完成首次配置`。

### 方案 3：任何入口保证 `~/.thatperson/` 自动生成

- 把 `ensureConfigDir()` 上移到 `main()` 最顶部（`loadEnv()` 之后、`--version` 分支之前，`src/cli.ts:730` 附近），使**任何一次 `thatperson` 调用（含 `--version` / `--help`）都保证目录存在**，从根上消除「验证版本号时目录不存在」的体感。
- 顺带把 `history/` 并入 `ensureConfigDir()` 的子目录清单（对齐 `src/config.ts:4` 注释声明），或至少在校验文档中写明 `history/` 由 store 初始化创建。
- 可选：config.json 首次生成时写入 `configured: false` 作为「首次运行标记」，供方案 2 的向导判断使用。

### 文档同步（《使用说明.md》《README.md》在「需要持续更新的文件.txt」清单内）

- 全局安装章节：删掉「在**自己的工作目录**创建 .env」的引导，改为「首次运行自动弹出配置向导，或执行 `thatperson setup`」；
- 首次配置章节：Key 配置统一走向导 / `config set apiKey`，说明优先级（环境变量 > config.json）；
- 目录表（`使用说明.md:111-115`）补充 config.json 现含 Key 字段（掩码展示）、history 目录初始化说明；
- 故障排查（`使用说明.md:130`）「对话报无 Key」条目更新为指向向导。

## 七、追加核查（2026-08-12）：用户级 present 空目录 与 history 测试记忆发布风险

> 追加动机：部署反馈之外，提出两点存疑——①用户级 `~/.thatperson/present/` 为空是否刻意、是否影响输出；②项目 `history/` 中关于羽毛球/篮球的测试归档是否已随出厂设定发布至 npm（若发布即工作纰漏）。

### 7.1 用户级 `~/.thatperson/present/` 为空 —— 刻意为之，不影响输出【已实证】

- **现状**：本机 `C:\Users\不辞水\.thatperson\present\` 为空目录；`~/.thatperson/` 下含 `history/ logs/ present/ skills/ config.json .last-update-check`。
- **定性**：这是**刻意设计的扩展层**。`loadPresent()`（`src/present.ts:31-60`）的加载级联 = **用户级 present（空）→ 项目级 present（5 文件，仅项目模式）→ 出厂级（包内 present/，缺名补齐）**。用户级 present 只是「用户可放入自己的覆盖文件」的占位目录，出厂时为空完全正常。
- **实证**：直接调用编译产物 `node -e "require('./dist/src/present.js').loadPresent(process.cwd())"` 返回 **3305 字符**、含 persona 特征串 → 出厂人格完整加载，**输出不受影响**。
- **全局部署同理**：npm 包 `files` 含 `present/`（5 个出厂 md），`PACKAGE_PRESENT_DIR` 兜底（`src/present.ts:15`）保证非项目模式下人格不空。
- **结论**：**非 Bug，不影响输出质量**。唯一可优化项：文档未明说「用户级 present 默认为空属正常、可自行放入覆盖文件」，建议在《使用说明.md》目录表处补一句。

### 7.2 history 测试记忆（羽毛球/篮球）是否发布至 npm —— 未发布【已实证】；但仓库卫生存在缺口

- **现状**：`history/profile/preferences.md` 与 `history/experiences/journal.md` 确有 2026-08-10 的「打篮球 / 打羽毛球」测试归档；且**已被 git 跟踪**（`git ls-files history/` 共 6 个文件），`.gitignore` **未**忽略 `history/`。
- **发布核查（实证）**：`npm pack --dry-run --json` 实际发布清单共 **51 个文件** = `dist/` + `present/`（5）+ `skills/` + `package.json` + `README.md`，**无 `history/`**。`package.json` 的 `files: ["dist","present","skills"]` 白名单不含 history → **测试记忆未随包发布**。`.env`、`API-key.md` 也未跟踪、未发布。
- **出厂 present/ 内容核查**：`present/` 中出现的「篮球 / 咖啡」是**人格规则的示意示例**（`present/persona.md:10`、`present/behavior.md:15,27`），且 `behavior.md:17` 明确「不模仿示例的话题（尤其咖啡）作为真实记忆或画像」——是教学示例，**不是**用户测试记忆混入。
- **归责结论**：测试记忆未发布到 npm → **不存在「发布污染」**，谈不上 codex 或提示词层的发布纰漏。但「测试记忆留在产物里」的担忧在**仓库层面真实存在**：`history/` 已提交进 git 且未被忽略——虽未进 npm 包，却是未来发布流程的隐患（若将来改 `files` 白名单、或误发布旧构建）。
- **需承认的方案缺口**：上一版参考方案（§四）**没有**包含「发布前初始化 / 清洗 history」这一步骤，本次补入 §7.3。

### 7.3 补充建议（并入参考方案）

- **仓库卫生**：将 `history/` 加入 `.gitignore`。开发机项目级记忆不再入库，符合「记忆是用户私有数据」定位；全局部署模式记忆本就在 `~/.thatperson/history/`，不受影响。若担心开发期丢失，可保留 `history/README.md` 占位或写 `.gitignore` 例外。
- **发布清单断言**：在 `prepublishOnly` 增加一步——`npm pack --dry-run --json` 校验发布清单**不含** `history/`、`.env`、`API-key*`、任何 `sk-` 明文，命中即失败、中断发布。可写成独立脚本（如 `scripts/check-publish.js`）。
- **文档补充**：《使用说明.md》说明「用户级 present 默认为空属正常，可放入覆盖文件」。

## 八、设计方向确认（2026-08-12）：取消「项目级/用户级」二元，统一「主目录 + 随身目录」

> 负责人确认：部署人群只 `npm i -g` 部署 Agent、**不克隆本项目**，因此以后**不再刻意区分项目级与用户级**。用户级 `~/.thatperson/` 是唯一主存储；「目录级」只保留一条规则。

### 8.1 已确认的定位模型（覆盖 §四/§六 中的两层级联表述）

| 概念 | 定位 | 说明 |
| :-- | :-- | :-- |
| **主目录 `~/.thatperson/`** | 唯一主存储 | `present/ skills/ history/ config.json` 全在此。出厂时 present/skills 为空（present 内容由包内出厂兜底运行时提供），history/ 随真实会话自填。部署用户只需关心这一个目录。 |
| **随身目录 `cwd/.thatperson/`（可选）** | 唯一的「本地目录」概念 | 任意目录运行 `thatperson`，若 **cwd 下存在 `.thatperson/`** 则自动识别并执行其 `present/ skills/ history/ config`。不绑定「是否本项目」。 |
